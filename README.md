# AI-EnterExam-Task2 — Автоматизация обработки тикетов поддержки (PoC)

## Коротко

Это минимальный прототип системы автоматизации обработки обращений в поддержку (тикетов): определение темы тикета, оценка риска, маршрутизация в очереди обработки и (для безопасных кейсов) автоматическое завершение. Система пишет полную трассу событий и сохраняет данные в SQLite, а клиентское приложение позволяет генерировать и отправлять тикеты для демонстрации.

Демо покрывает два обязательных сценария:
- Safe (happy path): безопасный тикет → классификация → маршрутизация/автообработка → логирование.
- Risky / fallback: рискованный или низкоуверенный тикет → деградация в ручную обработку (human-in-the-loop) → логирование причины.

## Как запустить (рекомендуемый путь: backend + desktop client)

Требования:
- Python 3.11+

### 1) Установка зависимостей

```bash
python -m pip install -r requirements.txt
```

### 2) Обучить локальную модель темы (опционально)

Если файла `model_service/model.json` нет, сначала обучите NB-модель:

```bash
python model_training/train.py --log-level INFO
```

### 3) Запустить backend как демон (с автоперезапуском)

```bash
python service/supervisor.py --host 127.0.0.1 --port 18000
```

### 4) Запустить desktop client

```bash
python client/desktop_client.py --api-base http://127.0.0.1:18000 --gen-per-min 30
```

Ожидаемый результат:
- В desktop client можно нажать Start и начать генерацию тикетов из `client/sample_tickets.json`.
- Тикеты переходят по статусам `NEW → PROCESSING → RESOLVED/PENDING_REVIEW`.
- В консоли и в UI видны стандартизованные workflow-логи в формате `[timestamp] [LEVEL] [module] message`.

## Консольный PoC-пайплайн (дополнительно)

Для быстрой демонстрации “пайплайна” без backend/UI можно запустить:

```bash
python main.py
```

Ожидаемый результат:
- В консоли — workflow-логи (без печати JSON/объектов).
- Файл аудита: `logs/audit.jsonl` (по 1 строке JSONL на тикет).

## Какой сценарий демонстрируется

1. На вход подаётся тикет (текст + метаданные).
2. Система делает topic classification и вычисляет confidence.
3. Система применяет risk policy (safe/risky) и правила деградации при низкой уверенности.
4. Система маршрутизирует тикет в очередь или автоматически завершает safe кейс (в backend-сервисе).
5. Система сохраняет события и решение (аудит, трассировка, статусы).

## Что реализовано, а что только дизайн

Реализовано в PoC:
- Backend-сервис (FastAPI) + SQLite-хранилище + фоновой worker, статусная модель тикета и SSE события.
- Desktop client (Tkinter): генерация тикетов из `client/sample_tickets.json`, офлайн-кэширование (pending), допередача.
- Локальная модель темы (Naive Bayes) + опциональный внешний LLM-классификатор (с деградацией).

Только архитектурный дизайн (не реализовано полностью):
- Очереди/шины событий для асинхронных задач (генерация ответа, суммаризация, переобучение).
- Полноценная база знаний и версионирование контента.
- Мониторинг в проме (метрики/алерты) как инфраструктура.
- Политики доступа, PII-санитизация на уровне DLP, управление ключами.

## Допущения и ограничения

- Категории и риск-политики упрощены и рассчитаны на демонстрацию (PoC).
- Интеграция с реальным HelpDesk/CRM не реализована; используется REST API и симулятор клиента.
- Качество классификатора зависит от объёма и качества размеченных данных (в репозитории — небольшой датасет).

## Зачем это бизнесу (минимальная продуктовая часть)

Система снижает нагрузку на операторов за счёт автоматизации типовых запросов и ускоряет первый ответ пользователю за счёт мгновенной маршрутизации. Для инцидентов и всплесков нагрузки она помогает быстрее выделять массовые проблемы и направлять их в правильные очереди, не ломая SLA. Риск-контуры и человек-в-петле уменьшают вероятность отправки небезопасных или неверных ответов. Аудит-лог позволяет разбирать ошибки, улучшать правила/модели и контролировать качество и стоимость LLM-инференса.
