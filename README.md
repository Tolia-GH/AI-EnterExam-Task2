# AI-EnterExam-Task2 — Автоматизация обработки тикетов поддержки (PoC)

## Коротко

Это минимальный прототип AI/ML-системы для автоматизации обработки обращений в поддержку крупного онлайн-сервиса: определение темы и риска тикета, поиск релевантного контента (похожих тикетов/фрагментов базы знаний), формирование решения (черновик ответа или маршрутизация) и сохранение аудиторного лога.

Демо включает:
- Happy path: типовой низкорисковый тикет → классификация/поиск → предложение ответа/маршрута → логирование.
- Fallback / Risky path: рискованный или low-confidence тикет → эскалация оператору (human-in-the-loop) → логирование причины эскалации.

## Как запустить PoC

Требования:
- Python 3.11+ (или укажите вашу версию)

Запуск:
```bash
python main.py
```

Ожидаемый результат:
- В консоли выводятся стандартизованные workflow-логи (без печати JSON/объектов)
- Формируется файл аудита `logs/audit.jsonl` (по 1 строке JSONL на тикет)

## Модельная классификация (локально)

По умолчанию PoC использует правила. Опционально можно обучить и подключить локальную модель для topic classification.

### 1) Обучение модели

```bash
python model_training/train.py
```

Артефакты:
- `model_service/model.json` — обученная модель (минимальный Multinomial NB)
- `model_training/training_report.json` — метрики train/val/test

### 2) Запуск модели как сервиса

```bash
python model_service/server.py --host 127.0.0.1 --port 8001
```

Health-check:
- `GET http://127.0.0.1:8001/health`

Inference:
- `POST http://127.0.0.1:8001/classify` с JSON `{"text":"...","meta":{...}}`

### 3) Подключение сервиса к PoC

```bash
python main.py --classifier-url http://127.0.0.1:8001
```

## Какой сценарий демонстрируется

1. На вход подаётся mock-ticket (текст + метаданные).
2. Система определяет topic и риск (risk_level) + оценку уверенности (confidence).
3. Система находит похожий тикет или релевантный фрагмент базы знаний (упрощённо в PoC).
4. Система предлагает:
   - либо draft-ответ (для safe + high-confidence),
   - либо маршрут/эскалацию оператору (для risky или low-confidence).
5. Система пишет аудит-лог: вход, признаки, решение, уверенность, использованные источники/правила.

## Что реализовано, а что только дизайн

Реализовано в PoC:
- Минимальный пайплайн обработки тикета end-to-end (один safe + один risky/fallback).
- Правила/эвристики для риска и темы (или укажите, если используете модель/LLM).
- Простейший retrieval по локальному набору примеров (или заглушка).
- Аудит-лог решения.

Только архитектурный дизайн (не реализовано полностью):
- Очереди/шины событий для асинхронных задач (генерация ответа, суммаризация, переобучение).
- Полноценная база знаний и версионирование контента.
- Мониторинг в проме (метрики/алерты) как инфраструктура.
- Политики доступа, PII-санитизация на уровне DLP, управление ключами.

## Допущения и ограничения

- Категории тикетов и риск-политики заданы вручную и упрощены.
- Нет реальной интеграции с CRM/HelpDesk и каналами (email/chat/app) — входы мокируются.
- Нет реального SLA/рейтконтроля и бэкпрешера — только дизайн в документации.
- Работа с PII показана концептуально; в PoC можно демонстрировать только обезличенные примеры.

## Зачем это бизнесу (минимальная продуктовая часть)

Система снижает нагрузку на операторов за счёт автоматизации типовых запросов и ускоряет первый ответ пользователю за счёт мгновенной маршрутизации. Для инцидентов и всплесков нагрузки она помогает быстрее выделять массовые проблемы и направлять их в правильные очереди, не ломая SLA. Риск-контуры и человек-в-петле уменьшают вероятность отправки небезопасных или неверных ответов. Аудит-лог позволяет разбирать ошибки, улучшать правила/модели и контролировать качество и стоимость LLM-инференса.
