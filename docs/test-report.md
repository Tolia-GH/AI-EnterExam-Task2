# Отчёт о тестировании (классификация тем + маршрутизация)

## 1) Область тестирования

Проверялись следующие части системы:
- Подготовка данных и обучение локальной модели topic classification (Naive Bayes).
- Загрузка модели в backend и стабильность инференса (в т.ч. деградация при ошибках).
- Корректность маршрутизации (routing) и деградации в ручную обработку.
- Desktop client: генерация тикетов из `client/sample_tickets.json`, офлайн-кэширование, допередача.

Цель: убедиться, что система работает end-to-end и остаётся предсказуемой при сбоях (timeouts / недоступность зависимостей), с трассируемыми логами и аудиторной историей.

## 2) Проверка обучения модели

### 2.1 Датасет

- Файл: `data/labeled_tickets.csv`
- Разделение: train 80% / val 10% / test 10% (случайная выборка)

### 2.2 Конфигурация обучения

- Модель: Multinomial Naive Bayes (токены: латиница/цифры + китайские иероглифы как отдельные символы)
- Подбор гиперпараметра: `alpha ∈ {0.5, 1.0, 2.0}` по `val_accuracy`
- Артефакты:
  - `model_service/model.json`
  - `model_training/training_report.json`

### 2.3 Результаты (по текущему small dataset)

Текущие метрики в репозитории — это PoC-уровень (малый объём данных), они нужны, чтобы подтвердить работоспособность пайплайна обучения/загрузки/инференса:
- `best_alpha=0.5`
- `test_accuracy≈0.83`

Примечание: требование “95%+” по точности достижимо только при наличии существенно большего и репрезентативного исторического датасета (и/или более сильной модели). Для экзаменационного PoC мы фиксируем цель: стабильный инференс + правильная деградация + корректная маршрутизация.

## 3) Проверка backend-сервиса и деградации

### 3.1 Проверяемые сценарии

- Создание тикета по REST (`POST /tickets`).
- Автообработка safe+high-confidence (закрытие/результат).
- Эскалация в `PENDING_REVIEW` для risky / low-confidence.
- Запись событий в историю (SSE `/events`) и в БД.

### 3.2 Негативные кейсы

- Невозможность вызвать внешний LLM (если настроен) → fallback на локальную NB-модель.
- Некорректные входные данные (пустой текст/слишком короткий текст) → route-to-human.
- Повторная обработка: тикеты в `PENDING_REVIEW` не должны бесконечно перерабатываться worker’ом (исправлено).

## 4) Проверка desktop client

### 4.1 Сценарии

- Генерация тикетов из `client/sample_tickets.json` (templates) с заданной частотой.
- Отправка на backend по HTTP.
- Офлайн режим: при недоступности backend тикеты попадают в `pending`, после восстановления автоматически доправляются.
- Получение статусов через SSE и корректное отображение счётчиков:
  - Auto resolved (RESOLVED)
  - Escalated (PENDING_REVIEW)

## 6) Вывод и следующие шаги

- PoC-цепочка “генерация → классификация → маршрутизация → деградация → аудит/события” работает.
- Для production требуется: расширение датасета, более сильная модель, калибровка confidence, формализация SLO/SLA и полноценная observability-инфраструктура.
