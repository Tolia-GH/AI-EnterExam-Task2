# monitoring.md — наблюдаемость и контроль качества

## 1) Зачем мониторинг

- Обнаруживать деградации качества и сдвиги входящего потока (drift).
- Контролировать техническую стабильность (latency/error rate/очереди).
- Контролировать стоимость LLM и долю тикетов, для которых включается генерация ответа.
- Проверять, что система решает исходную задачу (время ответа, эскалации, reopen).

## 2) Технические метрики (SRE)

Hot path:
- Latency p50/p95/p99 (цель: ≤500 ms на классификацию/маршрутизацию).
- Error rate по компонентам (ingestion, classifier, retrieval, decision).
- Timeout rate / retry rate.
- RPS и всплески нагрузки.

Очереди и async:
- Queue depth / lag / age of oldest message.
- Worker throughput, retry count, DLQ size.

Внешние зависимости (LLM/векторное хранилище/KB):
- Availability, latency, rate-limit errors.

## 3) ML-метрики (качество и дрейф)

Качество (онлайн-приближения):
- Доля эскалаций по low-confidence.
- Disagreement rate: модель vs решение оператора (approve/edit).
- Reopen rate по сегментам (класс/канал/язык/риск).

Дрейф:
- Сдвиг распределения входных признаков (длина текста, язык, частотные n-граммы).
- Сдвиг распределения эмбеддингов (PSI/KS/кластерные изменения).
- Рост доли “unknown/other” категории.

## 4) Бизнес-метрики (минимальный набор для AI-программы)

- SLA первого ответа (time-to-first-response) и доля нарушений SLA.
- CSAT (сегментировано: авто/ручная обработка).
- Reopen rate (особенно для автообработанных).
- Доля тикетов, закрытых/обработанных без участия оператора (при сохранении guardrails).

## 5) Мониторинг стоимости LLM

- Cost per ticket (средняя/percentiles) по потокам.
- % тикетов, для которых вызывается LLM (response generation).
- Среднее число токенов на тикет, стоимость по моделям/провайдерам.
- “Runaway” алерты: резкий рост токенов, рост частоты вызовов, рост ошибок/ретраев.

## 6) Стартовые алерты (MVP)

- p95 latency hot path > порога (например, 500 ms) N минут.
- Error rate > X% по критичным компонентам.
- Queue lag > Y минут.
- LLM API unavailable / rate-limited > X% запросов (response generation).
- Резкий рост доли risky или unknown категории.
- Reopen rate автообработанных > порога.

## 7) Как отличить деградацию модели от изменения входящего потока

- Если drift-метрики растут, а качество падает по многим категориям → вероятен input shift.
- Если drift-метрики стабильны, но растёт disagreement с операторами → вероятна деградация модели/правил.
- Сегментация: по каналам, языкам, категориям, инцидентам (всплески).

## 8) Аудит и расследования

- Audit Log должен позволять:
  - восстановить вход (обезличенный), решение и причину
  - увидеть evidence retrieval и версии моделей/правил/промптов
  - собрать выборку “плохих кейсов” для анализа

## 9) Что есть в PoC (as-built)

- Backend отдаёт агрегированные метрики через `GET /metrics` (throughput и распределение статусов).
- Desktop client использует `GET /events` (SSE) как источник событий для обновления UI-счётчиков.
- Для production требуется экспорт метрик в систему мониторинга (Prometheus/OpenTelemetry) и алерты по SLO.
