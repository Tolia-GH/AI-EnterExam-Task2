# AI_USAGE

Этот файл — честное описание того, как использовались AI-инструменты в процессе выполнения задания.

## 1) Понимание задачи и декомпозиция

- Инструмент(ы): чат-ассистент для проектирования/кодинга (TRAE).
- Что делал(а) с помощью AI:
  - Быстро разобрал(а) требования из `Requirements.md` и выделил(а) “must-have” артефакты (README + docs/* + AI_USAGE + SELF_REVIEW + PoC).
  - Зафиксировал(а) PoC критерии (safe vs risky/fallback), формат логов и требования по деградации.
- Вопросы к AI:
  - Как минимально реализовать пайплайн: классификация → риск → маршрутизация → аудит.
  - Как организовать демонстрацию: консольный PoC и отдельный backend+client для 7×24 режима.
- Решения, которые принял(а) сам(а):
  - Выбрал(а) доменную постановку “платформа доставки еды” и минимальную таксономию тем.
  - Зафиксировал(а) принцип безопасности: risky/low-confidence всегда в human-in-the-loop.

## 2) Проектирование архитектуры

- Инструмент(ы): TRAE.
- Какие варианты архитектуры предлагались:
  - Минимальный консольный PoC (single-run).
  - Непрерывный backend-сервис с worker’ом и отдельным desktop client.
- Что принято и почему:
  - Backend (FastAPI) + SQLite + worker + SSE: просто, воспроизводимо, достаточно для PoC и хорошо маппится на целевую архитектуру.
  - Desktop client на Tkinter: кроссплатформенно без дополнительных GUI зависимостей.
- Что отклонено и почему:
  - Сложные внешние инфраструктурные компоненты (Kafka/Redis/Vector DB) — только дизайн в документации, чтобы уложиться во временной бюджет.
- Что изменилось в финальном дизайне:
  - Добавлен supervisor для автоперезапуска backend-процесса.
  - Добавлен офлайн-буфер в client через `client/sample_tickets.json` (pending) и автоматическая допередача.

## 3) Выбор ML/LLM-подходов

- Инструмент(ы): TRAE.
- Как AI помог с выбором:
  - Для hot path предложен лёгкий классификатор (Naive Bayes) и/или правила, чтобы держать низкую задержку и стабильность.
  - Внешний LLM оставлен как опциональный topic classifier (OpenAI-compatible) с обязательным fallback.
- Где сознательно не использую LLM:
  - Для risky категорий (платежи/безопасность) без человека-в-петле.
  - Как единственный компонент hot path (из-за стоимости/нестабильности/таймаутов).

## 4) Разработка PoC

- Инструмент(ы): TRAE.
- Где AI ускорил написание кода:
  - Каркас backend-сервиса (REST endpoints, SSE).
  - Обвязка вокруг модели (загрузка артефакта, деградация при ошибках).
  - Desktop client: генерация тикетов, офлайн-очередь, UI-счётчики.
- Что делал(а) вручную:
  - Приведение логов к единообразному формату.
  - Уточнение доменной таксономии и правил маршрутизации.
- Как проверял(а) корректность:
  - Smoke/юнит тесты (tests/*).
  - Проверка сценариев: backend недоступен → client пишет pending → после восстановления допередача.

## 6) Поиск рисков, edge cases и ограничений

- Инструмент(ы): TRAE.
- Риски, найденные AI:
  - Недоступность модели/LLM → обязательная деградация.
  - PII и safety → маскирование и запрет автообработки risky.
  - Повторная обработка тикета в ручном статусе → риск “бесконечного цикла”.
- Риски, найденные дополнительно:
  - Несоответствие порта backend в клиенте → таймауты; исправлено настройкой `--api-base`.
  - Дублирование событий в UI → счётчики должны быть по ticket_id, а не по числу событий.
- Принятые меры:
  - Human-in-the-loop для risky/low-confidence.
  - Fallback на локальную модель при ошибках LLM.
  - Событийный лог (SSE) и аудит в SQLite/логах.

## 7) Примеры ошибок AI и как они были исправлены

Пример 1:
- Ошибка: в ранней версии worker повторно обрабатывал тикеты в `PENDING_REVIEW`, что раздувало счётчик “эскалаций”.
- Как заметил(а): UI показывал рост “Escalated” без новых тикетов.
- Как исправил(а): worker стал выбирать только `NEW` тикеты; UI-счётчики переведены на модель “ticket_id → статус”.

Пример 2:
- Ошибка: клиент падал при `TimeoutError`, т.к. не ловил исключение.
- Как заметил(а): генераторный поток прекращал работу с traceback.
- Как исправил(а): добавлен catch для TimeoutError и офлайн-кэширование в `pending` с последующей допередачей.
